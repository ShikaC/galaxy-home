# Galaxy 新版产品需求：任务与时间管理 + AI

更新日期：2026-09-10。状态：产品方向与重构需求；尚未完成新版功能实现。

本文是新版产品需求的主要入口。当前代码能力见 [README](../README.md)；下一位执行者从 [handoff](handoff.md) 开始。旧版说明书和历史决策用于理解已有实现，不再限定新版产品范围。用户后续明确要求优先于本文。

## 1. 产品方向与决策状态

用户明确希望做一款“类滴答清单 + AI 智能集成”的应用，并要求更新项目文档、生成交接材料。新版以任务和时间管理为中心，AI 参与记录、整理、安排、执行与调整。目标是用户能够每天依赖的效率工具，同时积累可核查的 AI 应用 / Agent 工程证据。

采用的工作路线是上一轮讨论建议：在现有仓库中重构，重建任务与时间核心，复用已验证的基础能力。具体数据结构、导航和平台方案在实施时通过场景验证确定；本文中的建议默认不代表用户已逐项指定了实现细节。

产品体验主线：**随手记录 → 整理任务 → 安排时间 → 执行 → 处理变化 → 回顾调整**。

- 任务与日历承载日常工作；笔记、项目、习惯和回顾提供支持。
- AI 能减少录入、整理和重新安排的操作，使用真实数据，并清楚展示依据与变更。
- 手动核心流程在 AI 未配置、网络不可用或模型失败时仍然可用。
- 保留数据的本地可用性与用户控制，同时将跨设备使用纳入产品目标。
- 以滴答清单的任务管理场景作为功能参照，形成自己的信息架构和视觉表达。

滴答清单官方已有 AI 语音、录音总结与 MCP / CLI 接入，因此“有聊天入口”不足以定义差异。Galaxy 优先验证的价值是：结合任务、知识与实际可用时间，提供可解释、可调整、可确认的持续规划。[官方功能](https://dida365.com/features?language=zh_CN) · [官方 AI 功能](https://help.dida365.com/articles/7444671678778441728)

## 3. 功能需求与验收方向

P0、P1、P2 表示实施次序；后续能力不会因优先级较低而成为永久禁止项。

| 编号 | 优先级 | 需求 | 验收方向 |
| --- | --- | --- | --- |
| TASK-01 | P0 | 快速创建、编辑、完成、恢复任务；清单 / 标签、优先级、父子关系 | 同一任务在列表、详情、今日和项目中的状态一致；批量操作有明确结果 |
| TIME-01 | P0 | 区分截止时间、安排时段、预计耗时、全天日期和固定日程 | 不把截止时间当作开始时间；日期任务跨时区保持正确语义，时段可用于冲突检查 |
| REPEAT-01 | P0 | 常见日 / 周 / 月重复、工作日规则、单次跳过 / 修改与历史 | 本次实例与系列可区分；完成实例不删除历史；重试或同步不重复生成实例 |
| REMIND-01 | P0 | 提醒绑定任务或重复实例，支持提前量 / 多提醒与延期 | 修改时间后旧提醒失效；拒绝通知权限、睡眠恢复和重复调度都有清楚行为 |
| CAL-01 | P0 | 日 / 周日历、拖动安排、未安排任务与时间容量 | 从日历调整后列表同步；固定事件与可移动任务可区分；超负荷不能悄悄通过 |
| AI-01 | P1 | 自然语言录入多任务及日期、优先级、清单和重复信息 | 保存前可修改识别结果；有歧义时追问；失败时保留原文供手动创建 |
| AI-02 | P1 | 基于已有安排的规划与重排 | 展示移动 / 新建 / 保持不变的任务、理由、约束冲突；确认当前版本后再执行 |
| AI-03 | P1 | 保持可控执行，并改善检索与语义质量 | 约束由应用验证；输入变化触发冲突处理；质量评测包含真实漏检、误排和引用不支持结论的反例 |
| FLOW-01 | P1 | 快捷键、批量操作、筛选排序与可保存视图 | 常见整理无需逐项打开详情；键盘操作、中文输入法和移动触控均可完成核心路径 |
| DEVICE-01 | P1 | 手机记录、电脑继续处理，离线编辑后恢复同步 | 重复提交、并发编辑、删除与恢复有定义，冲突可见且不会静默丢数据 |
| DELIVERY-01 | P1 | 普通用户安装、升级、备份恢复和 AI 连接 | 在目标设备实际验证首次启动、升级与恢复；运行时依赖有明确交付方案 |
| REVIEW-01 | P1 | 将完成、修改、延期和实际耗时反馈给后续规划 | 用户可纠正记录与偏好；建议与真实数据关联，能判断下一次安排是否改善 |
| EXT-01 | P2 | 外部日历、导入迁移、MCP / API、共享协作等扩展 | 根据首轮持续使用结果选择具体范围；外部读写沿用权限、变更确认和核验机制 |

“工作日”第一步可使用明确的周一至周五定义；若涉及法定节假日，需要另行确定日历数据来源与地区规则。应用退出后的提醒需采用目标平台允许的机制，设备关机期间不承诺即时送达，恢复后需补显与去重。

## 4. 建议的产品语义

以下用于指导模型设计，实施前需把迁移映射和用户行为写清楚。具体表结构、库选择、字段名与层级限制尚未定稿。

| 概念 | 含义与需要保持的区别 |
| --- | --- |
| 任务 | 可执行、可完成的事项；完成状态与是否已安排时间分别表达 |
| 清单 / 标签 | 清单负责主要组织，标签负责跨维度筛选；现有多分类关系如何迁移需明确，避免丢失归属 |
| 项目 / 子任务 | 项目承载目标与成果，子任务承载任务分解；两者不相互冒充 |
| 截止时间 / 安排时段 | 截止时间表达最晚完成要求；安排时段表达计划何时执行 |
| 全天日期 / 时间点 | 全天日期是日历语义，不能一律转成 UTC 零点；实际时间点需保存足够的时区信息 |
| 重复系列 / 实例 | 系列定义规则，实例保留某次执行、提醒和例外；需要稳定身份以支持幂等与同步 |
| AI 变更提案 | 对当前数据快照提出的新增或修改；包含版本、理由和约束检查结果 |
| 执行结果 | 已将确认的变更持久化并核验；不等于用户已经完成这些任务 |

现有“今日主要最多 3 项、重点唯一、其余放稍后”是旧实现的安排策略。新版应重新评估为可选聚焦方式，不能限制完整的今日任务与日历容量。独立的 `/plans` 入口已退役：“从笔记做计划”并入 `/task-plans` 的 plan 模式，能力不减少，入口由任务与日历的高频流程决定。

## 5. 首个完整交付场景

输入：“每个工作日检查客户反馈，周五提交方案。” 用户为方案添加子任务，并在本周日历安排时间；临时增加会议后，让 AI 调整剩余任务，查看变更后确认。刷新、重启后数据一致，下一次重复实例及提醒继续正确工作。

需要逐项验证：

1. 重复系列、周五截止任务及子任务正确建立；用户能修改 AI 识别结果。
2. 列表、详情、今日、日历读取同一任务状态；取消编辑不会残留写入。
3. 本周安排计入已有任务、固定会议、工作时段与预计耗时。
4. AI 不移动固定会议、不重新打开已完成任务；没有可行安排时明确说明冲突。
5. 变更预览清楚显示修改前后、原因和未解决事项；用户可以调整提案。
6. 预览后另一个窗口修改相关任务，旧版本确认被拒绝且保留本地调整。
7. 确认后原子写入并核验；重复确认不重复创建任务、时段或重复实例。
8. 模型失败、取消、断网后手动路径可继续；迟到响应不覆盖取消状态。
9. 完成或跳过单次重复实例后，历史与后续实例正确；提醒重试不重复投递。
10. 旧数据迁移后，任务、分类关系、日期安排、历史 AI 记录和备份恢复仍可用。

首个交付场景聚焦任务与时间核心。跨设备同步和安装体验作为后续独立验收项，不能因为此场景通过就宣称新版产品已全部完成。

## 6. 重构取舍与实施顺序

| 范围 | 处理方式 |
| --- | --- |
| React / TypeScript、Fastify / SQLite、Tauri | 保留当前基础，只有验证出明确阻碍时才替换；跨端方案单独评估 |
| 备份、恢复、迁移、回收站、模型与代理连接 | 复用并适配新数据结构，保持既有正确性 |
| AI 校验、确认、事务、幂等、版本、执行核验 | 保留机制，逐步支持更新 / 重排语义，不绕过服务端校验 |
| 任务、日期关联、重复和提醒模型 | 重点重建，提供升级迁移与回退方案 |
| 导航、工作台、任务详情、日历 | 围绕高频操作重新设计，复用组件与设计变量 |
| 笔记、习惯、专注、回顾 | 保持当前功能，按主流程需要逐步融合 |

| 阶段 | 可交付结果 | 进入下一阶段的依据 |
| --- | --- | --- |
| M0：建立模型与迁移方案 | 任务 / 时间 / 重复语义、旧新映射、提醒平台策略及首场景实施计划 | 模型能表达首场景；迁移覆盖现有数据；实现者可开始第一项变更 |
| M1：任务与重复核心 | 手动创建 / 编辑 / 完成、子任务、重复与提醒 | 正常路径、例外、时间边界和迁移回归通过 |
| M2：日历与容量 | 日 / 周安排、固定事件、未安排任务与冲突反馈 | 多视图一致；安排与调整可在实际 UI 中完成 |
| M3：AI 录入与重排 | 新任务识别、基于容量的提案、变更确认与执行核验 | 第 5 节完整场景通过，真实模型结果与固定回归分别记录 |
| M4：跨端与交付 | 移动记录、同步、安装升级与恢复 | 两设备并发 / 离线及目标平台实际验证通过 |
| M5：持续使用与深化 | 连续使用反馈、质量改进与选定外部集成 | 依据采纳、修改、放弃、完成和重排数据选择下一项工作 |

M0 起就评估同步需要的身份、版本与删除语义，避免 M4 再推翻任务模型；账号、同步协议、移动端技术与云服务供应商尚未选定。实施采用可回退的小步替换，保留可运行基线。

## 7. 验证与用户价值

- 工程：结构校验、事务、幂等、并发、时区、重复例外、导入升级和恢复失败分别验证；已有保障适配新模型继续成立。
- 产品：真实 UI 覆盖创建、整理、安排、完成与重排；同时验证无 AI、失败、取消、空数据与长内容。视觉细节见 [DESIGN.md](../DESIGN.md)。
- 模型：结构 / 状态硬性检查与语义质量分开；人工检查引用支持、安排可行性和产出价值，记录模型、提示词版本、样本数、延迟与 token。
- 性能：建立大量任务、重复实例、长笔记与低配置设备的数据集，实际测量响应与内存后确定目标；当前没有规模性能结论。
- 使用：首轮建议持续至少两周，记录计划采纳 / 修改 / 放弃、重排原因、任务完成及整理耗时；仅使用自愿提供且脱敏的记录。
- 发布：记录目标平台、版本和证据；Windows 历史验收不自动证明当前 macOS、移动端或新版模型的交付质量。

## 8. 需要在实施中定下的设计选择

清单与现有多分类的映射；父子任务完成规则；重复实例生成与系列修改语义；全天 / 跨时区时间处理；通知调度与退出行为；同步冲突和身份模型；移动端与安装运行时方案；AI 变更提案兼容旧运行记录的方式。

这些选择需要先检查现有代码并给出有依据的默认方案。只有产品取舍无法从目标推断、或需要用户提供外部条件时再提出具体问题；避免把常规实现选择变成反复确认。
